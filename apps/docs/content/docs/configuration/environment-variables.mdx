# Environment Variables

<PageInlineTOC>Jump to variable group</PageInlineTOC>

Jose Madrid Salsa uses environment variables for all secrets, API keys, and runtime configuration. Variables prefixed with `NEXT_PUBLIC_` are exposed to the browser; all others are server-only.

<Callout type="warn">
Never commit `.env` files to version control. Use `.env.example` as a reference template and configure real values in Vercel or your local `.env.local` file.
</Callout>

## Database

| Variable | Required | Description |
|---|---|---|
| `DATABASE_URL` | Yes | Primary PostgreSQL connection string (pooled). Falls back to `PRISMA_DATABASE_URL` then `POSTGRES_URL` if unset. |
| `DATABASE_URL_UNPOOLED` | Recommended | Direct (non-pooled) connection for migrations. Used by Prisma `directUrl`. |
| `PRISMA_DATABASE_URL` | No | Alias fallback for `DATABASE_URL`. |
| `POSTGRES_URL` | No | Second fallback for `DATABASE_URL`. Vercel Postgres integration sets this automatically. |

```bash title=".env.local"
DATABASE_URL="prisma+postgres://accelerate.prisma-data.net/?api_key=..."
DATABASE_URL_UNPOOLED="postgresql://user:pass@ep-xxx.us-east-2.aws.neon.tech/josemadridsalsa?sslmode=require"
```

## QuickBooks Online

The Client ID and Secret are optional here — the preferred place to enter them is
**Admin → Settings → Integrations**, which stores the secret encrypted in the database. These
variables exist as a fallback and are read only when no admin-entered credentials are present.

`QUICKBOOKS_ENVIRONMENT` has no admin-panel equivalent and **must** be set to reach real company
data: it defaults to `sandbox`, and the Connect button on the integrations page connects to
whichever environment it names. Left unset in production, the flow completes successfully against
an Intuit *sandbox* company and syncs nothing real.

| Variable | Required | Description |
|---|---|---|
| `QUICKBOOKS_ENVIRONMENT` | To reach live books | `sandbox` (default) or `production`. Selects both the Intuit API host and which stored credential set is used. |
| `QUICKBOOKS_CLIENT_ID` | No | Intuit app Client ID. Fallback only; admin-entered credentials win. |
| `QUICKBOOKS_CLIENT_SECRET` | No | Intuit app Client Secret. Fallback only; admin-entered credentials win. |

The redirect URI is derived from `NEXTAUTH_URL` as `{NEXTAUTH_URL}/api/integrations/quickbooks/callback`
and must be registered verbatim in the Intuit app. Sandbox and production keys are different pairs,
and credentials are stored per environment — production keys saved while the app is in sandbox mode
are filed under `sandbox` and will not work.

## BigCommerce

BigCommerce is the system of record for catalog, carts, checkout and orders; this app is a
headless storefront on top of it. Jose Madrid runs **two** BigCommerce stores, and each needs its
own store-level API account (BigCommerce admin → **Settings → API → Store-level API accounts**).
Product ids are per store, so the two sets must never be swapped. A store with any of its four
variables unset is treated as not configured.

| Variable | Required | Description |
|---|---|---|
| `BIGCOMMERCE_STORE_HASH` | For the storefront | Main store (josemadridsalsa.com) hash — the part after `/stores/` in the API path. |
| `BIGCOMMERCE_ACCESS_TOKEN` | For the storefront | Main store API account access token. |
| `BIGCOMMERCE_CLIENT_ID` | For the storefront | Main store API account client ID. |
| `BIGCOMMERCE_CLIENT_SECRET` | For the storefront | Main store API account client secret; also signs customer-login tokens. |
| `BIGCOMMERCE_FUNDRAISING_STORE_HASH` | For fundraising orders | Fundraising store (josemadridsalsafundraising.com) hash. |
| `BIGCOMMERCE_FUNDRAISING_ACCESS_TOKEN` | For fundraising orders | Fundraising store API account access token. |
| `BIGCOMMERCE_FUNDRAISING_CLIENT_ID` | For fundraising orders | Fundraising store API account client ID. |
| `BIGCOMMERCE_FUNDRAISING_CLIENT_SECRET` | For fundraising orders | Fundraising store API account client secret. |
| `BIGCOMMERCE_FUNDRAISING_STOREFRONT_URL` | No | Fundraising store's storefront origin, where its hosted checkout and checkout form fields live. Defaults to https://josemadridsalsafundraising.com. |
| `NEXT_PUBLIC_FUNDRAISING_SITE_URL` | No | Canonical origin of the fundraising site (canonicals, sitemap, robots). Defaults to https://fundraising.josemadrid.net. |
| `FUNDRAISING_SITE_HOSTS` | No | Extra comma-separated hosts that serve the fundraising site, e.g. josemadridsalsafundraising.com once its DNS points here. |
| `NEXT_PUBLIC_COMMERCE_BACKEND` | At cutover | Set to `bigcommerce` to switch the storefront over: product prices and stock come from BigCommerce, and retail carts check out in BigCommerce's hosted checkout. Unset, the site prices and checks out as before. Fundraiser carts keep this site's checkout either way. Build-time: redeploy after changing it. |
| `BIGCOMMERCE_CHANNEL_ID` | No | BigCommerce channel carts are created in. Defaults to `1`, the existing storefront, whose checkout is served on josemadridsalsa.com — correct while that domain still points at BigCommerce. Once the domain points at this site, set it to the headless channel whose checkout domain is a subdomain. |
| `BIGCOMMERCE_ORDERS_TO_QUICKBOOKS` | No | `true` lets orders copied from either BigCommerce store (`importSource = bigcommerce` or `bigcommerce-fundraising`) flow into the hourly QuickBooks sync as sales receipts. Off by default: if online revenue already reaches QuickBooks another way, such as the Stripe and PayPal deposits, syncing these too would count every retail sale twice. Decide with whoever keeps the books before turning it on. |
| `BIGCOMMERCE_STOREFRONT_URL` | At domain cutover | Where the old BigCommerce storefront lives once josemadridsalsa.com points here, e.g. `https://shop.josemadridsalsa.com`. When set, legacy `login.php`, `account.php`, `giftcertificates.php` and `wishlist.php` links go there (temporary redirects, query string kept) so customers reach their BigCommerce account; unset, they go to this site's pages. Build-time. See the [cutover runbook](/docs/deployment/bigcommerce-cutover). |
| `BIGCOMMERCE_WEBHOOK_SECRET` | For live catalog updates | Shared secret BigCommerce sends in a header on every webhook; `/api/webhooks/bigcommerce` refuses calls without it (and refuses everything when it is unset). Any long random string. Register the hooks after deploying with `npm run bigcommerce:webhooks --workspace @jose-madrid/storefront -- https://<site-origin>` (add `--store fundraising` for the fundraising store), run with production's values; re-run it to revive hooks BigCommerce disabled after an outage. |

The API accounts need **modify** on Products, Carts, Checkouts, Customers, Channel settings and
Sites & routes, and **read-only** on Orders and Information & settings. The main store's account
also needs **Themes: modify** (and Content: modify is useful) for the checkout-theme tooling
(`npm run bigcommerce:theme`). A `403 You don't have a
required scope` on every call means the account was saved with no scopes; a `401` means the token
or store hash is wrong.

<Callout type="warn" title="Set the warehouse address">
Rate quoting and label purchase both read the warehouse address through
`lib/shipping/origin.ts`, which takes **Settings → Shipping** first and these variables second.
Until one of the two is complete, no real carrier rate can be fetched — checkout falls back to
flat-rate estimates and logs why.

They used to be configured separately: quoting read `SHIPPING_ORIGIN_*` and **defaulted to a
placeholder address in San Francisco** when unset, while label purchase read `SHIP_FROM_*`. A
half-configured deployment therefore quoted customers from one address and shipped from another,
with nothing in the response to indicate it.
</Callout>

## Customer Email Triage

The Gmail triage reuses the Google OAuth client and the Anthropic key; it adds no variables
of its own. The mailbox grant itself is stored encrypted in the database, not in the
environment — connect it at `/admin/inbox/settings`.

| Variable | Purpose |
| :--- | :--- |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | The OAuth client the Gmail grant is made against. Needs `gmail.modify` and `gmail.send` on its consent screen, and `/api/admin/inbox/google/callback` as a redirect URI. |
| `ANTHROPIC_API_KEY` | Classifies each message and writes the reply. Without it every email escalates to a human rather than going unread. |
| `ANTHROPIC_MODEL` | Optional override; defaults to `claude-opus-5`. |
| `CRON_SECRET` | Guards `/api/cron/inbox-triage`, as it does every scheduled route. |
| `MASTER_KEY` / `ENCRYPTION_KEY` | Encrypt the stored Gmail tokens at rest. |

## Internal

| Variable | Required | Description |
|---|---|---|
| `SERVICE_API_KEY` | No | Shared secret for internal service-to-service API calls |

**Moving the site to another domain:** set `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_BASE_URL`,
`NEXT_PUBLIC_APP_URL` and `NEXTAUTH_URL` to the new origin in Vercel (production), update
**Admin → SEO → Site URL** (`SeoConfiguration.siteUrl`), and redeploy. No code change is needed.
